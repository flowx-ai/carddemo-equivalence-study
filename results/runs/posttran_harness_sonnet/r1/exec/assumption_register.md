# Assumption ledger (extracted verbatim from the Calculate Posting script)

1. **delivery-scope**: This implementation receives decoded records and returns arrays and assumptions text, not physical files; file delivery is a separate connection. _Basis:_ posttran-sonnet.pdf p.27 specifies file inputs and outputs. Maker explicitly chose calculation results and assumptions text without that connection.
2. **input-layouts**: Input arrays use the contract field names. No fixed-width offsets, filler bytes or signed-overpunch decoding are guessed. _Basis:_ posttran-sonnet.pdf pp.7,9-12,27 reference copybooks and lengths but do not supply complete byte layouts.
3. **required-arrays**: All four input arrays must be supplied explicitly. An empty array is valid; a missing array is a batch error, not an empty file. _Basis:_ posttran-sonnet.pdf p.27 lists run inputs; behaviour for missing decoded input arrays is absent.
4. **money**: Use signed integer cents with safe-integer overflow checks, reject values having more than two decimal places, and emit amounts as two-decimal JSON strings without rounding. _Basis:_ posttran-sonnet.pdf pp.7,9-10 describes two-decimal amounts; p.27 allows strings or numbers with at most two decimals. Rounding and arithmetic implementation are unspecified.
5. **identity**: Preserve supplied transaction IDs. Duplicate transaction IDs anywhere in a feed, or duplicate account, card-reference or composite category-balance keys, make the entire calculation an error before any publishable updates. _Basis:_ posttran-sonnet.pdf p.3 proposes transaction-ID idempotency, while pp.9,23 propose generated IDs. p.27 supplies transaction IDs but no sequence or prior-transaction input. Duplicate input handling is unspecified.
6. **processing-time**: Capture one UTC processing time per invocation unless a comparison timestamp is supplied. Emit YYYY-MM-DD HH:mm:ss.ffffff, padding runtime milliseconds to six fractional digits. Preserve original timestamps on rejected records. _Basis:_ posttran-sonnet.pdf p.3 says processedTimestamp = now; pp.9-10 give a 26-character processed timestamp. Timezone, precision and a comparison clock are unspecified.
7. **business-date**: The business date defaults to 2022-07-18. Expiry comparisons use the original transaction calendar date, not the business date; equality is allowed. _Basis:_ posttran-sonnet.pdf p.27 fixes business date 2022-07-18; p.3 BR-04 uses account expiry < transaction original date.
8. **dependent-checks**: A missing card reference yields 100 without attempting unavailable account checks; a missing account yields 101. When both limit and expiry fail on an available account, retain only 103. _Basis:_ posttran-sonnet.pdf pp.3-4 specifies xref then account then limit then expiry and last-reason overwrite, but p.4 also combines invalid card with expired account without explaining how that account is resolved.
9. **negative-debit**: A negative posted amount is added as a negative number to current cycle debit; it is not converted to its absolute value. _Basis:_ posttran-sonnet.pdf p.3 BR-05 explicitly says else currentCycleDebit += amount; alternative accounting-sign interpretations are not specified.
10. **zero-amount**: A zero-amount transaction is posted if reference, limit and expiry checks pass, and creates a zero balance category when none exists. _Basis:_ posttran-sonnet.pdf p.3 BR-05 uses amount >= 0 and creates a missing category balance; it does not give a separate zero-amount rule.
11. **no-extra-validation**: Do not reject solely for inactive status, absent type/category reference data, customer/card attributes, or the unused interest parameter; only the four documented business checks decide posting. _Basis:_ posttran-sonnet.pdf pp.3-4 lists posting business checks; p.27 lists additional chain input files and the INTCALC parameter but assigns no additional POSTTRAN check to them.
12. **representation**: Account IDs and merchant IDs are nonnegative JSON integers; transaction category codes are integers. Card numbers and transaction IDs stay strings. Category-balance category codes are four-character zero-padded strings, type codes stay strings, and only trailing ASCII spaces are removed from strings. _Basis:_ posttran-sonnet.pdf p.27 fixes account, merchant and transaction category integer types and permits omission of trailing spaces. p.10 calls category-balance category codes four-character strings; p.27 does not resolve their JSON type.
13. **optional-fields**: Missing optional account reissue date and ZIP are returned as empty strings. All required contract fields otherwise must be present in decoded records. Dates must be valid ISO calendar dates; original timestamps must begin with such a date. _Basis:_ posttran-sonnet.pdf p.7 marks reissue date and account ZIP optional; p.27 requires output fields. Defaults and malformed-input handling are unspecified.
14. **whole-snapshot**: Return every supplied account and category balance, including untouched rows, in supplied order; append newly created category balances in first-posted order. Output order carries no business meaning. _Basis:_ posttran-sonnet.pdf p.27 requires every account and category balance after posting and permits result objects in any order.
15. **errors**: Malformed decoded data, duplicate keys or unsafe arithmetic returns ERROR with null return code and no publishable output arrays. Do not manufacture a business reject or expose partially calculated balances. _Basis:_ posttran-sonnet.pdf pp.3-4 defines business rejects and WARNING/4, but no return code or publication policy for malformed decoded inputs or arithmetic failures.
16. **persistence-and-restart**: This pure calculation does not persist checkpoints, prevent duplicate external writes or resume midway. Repeating the same snapshots with the same timestamp recalculates the same financial results without incrementing those snapshots in place. _Basis:_ posttran-sonnet.pdf pp.3-4 proposes per-transaction persistence and restart without duplicates; the maker left the persistence/file connection for later, so those durable guarantees are not claimed.
17. **infrastructure-failures**: No account rewrite, external retry or reason-109 rejection is simulated. A later persistence integration must handle its own write failures without publishing partially updated state. _Basis:_ posttran-sonnet.pdf p.3 BR-08 says account rewrite failure 109 aborts a record and is not written to rejects; pp.17,19,21,23 describe external failure handling. This calculation has no such writes.
18. **reject-image**: Return the original decoded transaction fields with integer reason and unpadded reason text, not a reconstructed 350-byte image or 430-byte reject record. _Basis:_ posttran-sonnet.pdf p.3 BR-06 describes the legacy image and trailer; p.27 explicitly accepts JSON fields instead and permits omission of trailing spaces.
19. **assumptions-drafting**: A model drafts each assumption and wiki basis from this ledger only. Financial calculations never use its answers. Missing, duplicate or structurally incomplete drafting falls back to the full authoritative ledger; the ledger is always appended as the definitive decision record. _Basis:_ Maker requested every implementation decision and its wiki statement or absence. The confirmed description uses a separate model drafting step and deterministic fallback; the wiki prescribes no assumptions-document drafting method.
