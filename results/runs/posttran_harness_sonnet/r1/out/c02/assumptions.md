# Daily transaction posting assumptions

| What you assumed | Which wiki statement (or absence of one) it rests on |
|---|---|
| **delivery-scope:** The implementation accepts decoded records and returns arrays plus assumptions text rather than physical files. Physical file delivery remains a separate connection. | The selected delivery scope excludes the file connection described by the wiki. Original basis: posttran-sonnet.pdf p.27 specifies file inputs and outputs. Maker explicitly chose calculation results and assumptions text without that connection. |
| **input-layouts:** Decoded input arrays follow the contract's field names; fixed-width offsets, filler bytes and signed-overpunch decoding are not guessed. | Incomplete byte-layout evidence limits the implementation to decoded fields. Original basis: posttran-sonnet.pdf pp.7,9-12,27 reference copybooks and lengths but do not supply complete byte layouts. |
| **required-arrays:** Each of the four input arrays must be explicitly present. Empty arrays are permitted, but an omitted array is a batch error rather than an empty file. | The explicit-presence requirement addresses a gap in decoded-input handling. Original basis: posttran-sonnet.pdf p.27 lists run inputs; behaviour for missing decoded input arrays is absent. |
| **money:** Amounts use signed integer cents with safe-integer overflow checks. Values exceeding two decimal places are rejected, and output amounts are two-decimal JSON strings without rounding. | Decimal constraints are documented; the arithmetic and no-rounding choices address unspecified implementation details. Original basis: posttran-sonnet.pdf pp.7,9-10 describes two-decimal amounts; p.27 allows strings or numbers with at most two decimals. Rounding and arithmetic implementation are unspecified. |
| **identity:** Supplied transaction IDs are retained. Any repeated transaction ID anywhere in the feed, or repeated account, card-reference or composite category-balance key, makes the entire calculation an error before publishable updates exist. | Conflicting ID guidance and absent duplicate-input rules underlie the recorded choice. Original basis: posttran-sonnet.pdf p.3 proposes transaction-ID idempotency, while pp.9,23 propose generated IDs. p.27 supplies transaction IDs but no sequence or prior-transaction input. Duplicate input handling is unspecified. |
| **processing-time:** Each invocation captures one UTC processing timestamp unless a comparison timestamp is provided. Its format is YYYY-MM-DD HH:mm:ss.ffffff, with runtime milliseconds padded to six fractional digits. Rejected records retain their original timestamps. | The wiki supplies a current-time instruction and timestamp length but leaves clock details unspecified. Original basis: posttran-sonnet.pdf p.3 says processedTimestamp = now; pp.9-10 give a 26-character processed timestamp. Timezone, precision and a comparison clock are unspecified. |
| **business-date:** The default business date is 2022-07-18. Expiry is compared against the transaction's original calendar date, not the business date, and equal dates are allowed. | The business-date setting and strict expiry comparison support this distinction. Original basis: posttran-sonnet.pdf p.27 fixes business date 2022-07-18; p.3 BR-04 uses account expiry < transaction original date. |
| **dependent-checks:** An absent card reference produces reason 100 without unavailable account checks; an absent account produces 101. If an available account fails both limit and expiry checks, only reason 103 remains. | Check ordering and overwrite guidance support the choice, subject to an unresolved example. Original basis: posttran-sonnet.pdf pp.3-4 specifies xref then account then limit then expiry and last-reason overwrite, but p.4 also combines invalid card with expired account without explaining how that account is resolved. |
| **negative-debit:** A posted negative amount is added to current cycle debit with its negative sign intact, not as an absolute amount. | The recorded interpretation follows the stated signed addition rather than an unspecified alternative sign convention. Original basis: posttran-sonnet.pdf p.3 BR-05 explicitly says else currentCycleDebit += amount; alternative accounting-sign interpretations are not specified. |
| **zero-amount:** A zero-amount transaction posts when reference, limit and expiry checks pass. If its category balance is missing, a zero balance category is created. | The general nonnegative-amount and category-creation provisions are the support; no separate zero rule is supplied. Original basis: posttran-sonnet.pdf p.3 BR-05 uses amount >= 0 and creates a missing category balance; it does not give a separate zero-amount rule. |
| **no-extra-validation:** Only the four documented business checks determine posting. Inactive status, missing type/category reference data, customer/card attributes and the unused interest parameter do not alone cause rejection. | Additional chain inputs are not assigned additional POSTTRAN business checks. Original basis: posttran-sonnet.pdf pp.3-4 lists posting business checks; p.27 lists additional chain input files and the INTCALC parameter but assigns no additional POSTTRAN check to them. |
| **representation:** Account and merchant IDs are nonnegative JSON integers, and transaction category codes are integers. Card numbers and transaction IDs remain strings. Category-balance category codes are four-character, zero-padded strings; type codes remain strings. String trimming removes only trailing ASCII spaces. | The representation combines documented types with the recorded resolution of an unresolved category-balance JSON type. Original basis: posttran-sonnet.pdf p.27 fixes account, merchant and transaction category integer types and permits omission of trailing spaces. p.10 calls category-balance category codes four-character strings; p.27 does not resolve their JSON type. |
| **optional-fields:** Missing optional account reissue dates and ZIPs are returned as empty strings. Otherwise, every required contract field must be present in decoded records. Dates must be valid ISO calendar dates, and original timestamps must start with such a date. | Optionality and output requirements are documented, while defaults and malformed-input treatment are not. Original basis: posttran-sonnet.pdf p.7 marks reissue date and account ZIP optional; p.27 requires output fields. Defaults and malformed-input handling are unspecified. |
| **whole-snapshot:** All supplied accounts and category balances, including untouched rows, are returned in their supplied order. New category balances are appended in first-posted order. Ordering has no business significance. | Whole-snapshot coverage is required, while the chosen ordering is permitted rather than prescribed. Original basis: posttran-sonnet.pdf p.27 requires every account and category balance after posting and permits result objects in any order. |
| **errors:** Malformed decoded data, duplicate keys or unsafe arithmetic produce ERROR, a null return code and no publishable output arrays. They do not produce manufactured business rejects or expose partially calculated balances. | The recorded batch-error policy addresses failures outside the documented business-reject policy. Original basis: posttran-sonnet.pdf pp.3-4 defines business rejects and WARNING/4, but no return code or publication policy for malformed decoded inputs or arithmetic failures. |
| **persistence-and-restart:** This pure calculation neither saves checkpoints nor prevents duplicate external writes nor resumes partway through processing. Repeating identical snapshots with the same timestamp recalculates identical financial results without incrementing the supplied snapshots in place. | Proposed durable behavior is outside the calculation's scope and is not guaranteed here. Original basis: posttran-sonnet.pdf pp.3-4 proposes per-transaction persistence and restart without duplicates; the maker left the persistence/file connection for later, so those durable guarantees are not claimed. |
| **infrastructure-failures:** The calculation does not simulate account rewrites, external retries or reason-109 rejections. Any later persistence integration must manage its own write failures without publishing partially updated state. | External-write failure guidance does not imply simulated writes in this calculation. Original basis: posttran-sonnet.pdf p.3 BR-08 says account rewrite failure 109 aborts a record and is not written to rejects; pp.17,19,21,23 describe external failure handling. This calculation has no such writes. |
| **reject-image:** Reject output contains the original decoded transaction fields, an integer reason and unpadded reason text. It does not reconstruct a 350-byte image or a 430-byte reject record. | The JSON alternative supports decoded reject output instead of a reconstructed legacy record. Original basis: posttran-sonnet.pdf p.3 BR-06 describes the legacy image and trailer; p.27 explicitly accepts JSON fields instead and permits omission of trailing spaces. |
| **assumptions-drafting:** The recorded drafting design uses a model to draft each assumption and wiki basis solely from the ledger; financial calculations never use those answers. Missing, duplicate or structurally incomplete drafting triggers fallback to the full authoritative ledger, and the design always appends that ledger as the definitive decision record. | The drafting design rests on maker requirements and the confirmed description, not a wiki-prescribed method. Original basis: Maker requested every implementation decision and its wiki statement or absence. The confirmed description uses a separate model drafting step and deterministic fallback; the wiki prescribes no assumptions-document drafting method. |
