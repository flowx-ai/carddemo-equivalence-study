# Daily transaction posting assumptions

| What you assumed | Which wiki statement (or absence of one) it rests on |
|---|---|
| **delivery-scope:** The implementation accepts decoded records and supplies result arrays plus assumptions text. It does not deliver physical files; that requires a separate connection. | This is the ledger's delivery boundary rather than a replacement for the documented file interface. Original basis: posttran-sonnet.pdf p.27 specifies file inputs and outputs. Maker explicitly chose calculation results and assumptions text without that connection. |
| **input-layouts:** Decoded input arrays follow the contract's field names. The implementation does not guess fixed-width offsets, filler bytes, or signed-overpunch decoding. | The cited material does not provide enough layout detail to define byte-level decoding. Original basis: posttran-sonnet.pdf pp.7,9-12,27 reference copybooks and lengths but do not supply complete byte layouts. |
| **required-arrays:** Each of the four input arrays must be explicitly present. Empty arrays are accepted, but an omitted array causes a batch error rather than representing an empty file. | The ledger supplies the missing-array policy where the wiki is silent. Original basis: posttran-sonnet.pdf p.27 lists run inputs; behaviour for missing decoded input arrays is absent. |
| **money:** Amounts are handled as signed integer cents with safe-integer overflow checks. Values with more than two decimal places are rejected, and output amounts are two-decimal JSON strings with no rounding. | Decimal constraints are documented; the arithmetic representation and no-rounding implementation are ledger choices. Original basis: posttran-sonnet.pdf pp.7,9-10 describes two-decimal amounts; p.27 allows strings or numbers with at most two decimals. Rounding and arithmetic implementation are unspecified. |
| **identity:** Supplied transaction IDs are retained. Any duplicate transaction ID anywhere in the feed, or duplicate account, card-reference, or composite category-balance key, fails the entire calculation before any updates become publishable. | The ledger resolves the competing ID descriptions and the unspecified duplicate-input policy. Original basis: posttran-sonnet.pdf p.3 proposes transaction-ID idempotency, while pp.9,23 propose generated IDs. p.27 supplies transaction IDs but no sequence or prior-transaction input. Duplicate input handling is unspecified. |
| **processing-time:** Unless a comparison timestamp is provided, one UTC processing time is captured for the invocation. It is formatted as YYYY-MM-DD HH:mm:ss.ffffff, with runtime milliseconds padded to six fractional digits. Rejected records retain their original timestamps. | The ledger specifies clock conventions not settled by the cited timestamp requirements. Original basis: posttran-sonnet.pdf p.3 says processedTimestamp = now; pp.9-10 give a 26-character processed timestamp. Timezone, precision and a comparison clock are unspecified. |
| **business-date:** The default business date is 2022-07-18. Expiry is compared against the original transaction's calendar date, not the business date, and an equal expiry date is permitted. | The default date and strict expiry comparison have distinct cited bases. Original basis: posttran-sonnet.pdf p.27 fixes business date 2022-07-18; p.3 BR-04 uses account expiry < transaction original date. |
| **dependent-checks:** A missing card reference produces reason 100 without attempting unavailable account checks; a missing account produces 101. If an available account fails both limit and expiry checks, only reason 103 is retained. | The ledger follows the documented check order and overwrite rule while resolving the unexplained account-resolution case. Original basis: posttran-sonnet.pdf pp.3-4 specifies xref then account then limit then expiry and last-reason overwrite, but p.4 also combines invalid card with expired account without explaining how that account is resolved. |
| **negative-debit:** When a posted amount is negative, its signed negative value is added to current cycle debit; its absolute value is not substituted. | This preserves the cited signed addition without introducing another accounting-sign interpretation. Original basis: posttran-sonnet.pdf p.3 BR-05 explicitly says else currentCycleDebit += amount; alternative accounting-sign interpretations are not specified. |
| **zero-amount:** A zero-valued transaction posts when reference, limit, and expiry checks succeed. If its category balance is missing, a category with a zero balance is created. | The ledger applies the documented nonnegative branch and missing-category creation without adding a separate zero-value rejection. Original basis: posttran-sonnet.pdf p.3 BR-05 uses amount >= 0 and creates a missing category balance; it does not give a separate zero-amount rule. |
| **no-extra-validation:** Only the four documented business checks determine posting. Inactive status, missing type/category reference data, customer/card attributes, or the unused interest parameter do not alone cause rejection. | The cited additional inputs do not establish additional POSTTRAN business checks. Original basis: posttran-sonnet.pdf pp.3-4 lists posting business checks; p.27 lists additional chain input files and the INTCALC parameter but assigns no additional POSTTRAN check to them. |
| **representation:** Account and merchant IDs are nonnegative JSON integers, and transaction category codes are integers. Card numbers and transaction IDs remain strings. Category-balance category codes are four-character, zero-padded strings; type codes remain strings. String trimming removes only trailing ASCII spaces. | The ledger resolves the category-balance JSON-type gap and limits string trimming. Original basis: posttran-sonnet.pdf p.27 fixes account, merchant and transaction category integer types and permits omission of trailing spaces. p.10 calls category-balance category codes four-character strings; p.27 does not resolve their JSON type. |
| **optional-fields:** An absent optional account reissue date or ZIP is returned as an empty string. Otherwise, decoded records must contain every required contract field. Dates must be valid ISO calendar dates, and original timestamps must start with a valid date of that form. | Optionality is documented, while the defaults and malformed-input requirements are supplied by the ledger. Original basis: posttran-sonnet.pdf p.7 marks reissue date and account ZIP optional; p.27 requires output fields. Defaults and malformed-input handling are unspecified. |
| **whole-snapshot:** Results include every supplied account and category balance, even untouched rows, in their supplied order. New category balances are appended in first-posted order; output ordering has no business significance. | Complete snapshots are required, but the particular ordering is a ledger choice within the wiki's allowance. Original basis: posttran-sonnet.pdf p.27 requires every account and category balance after posting and permits result objects in any order. |
| **errors:** Malformed decoded records, duplicate keys, or unsafe arithmetic produce ERROR with a null return code and no publishable output arrays. Such failures neither become manufactured business rejects nor expose partially calculated balances. | The ledger defines this error and publication boundary separately from documented business rejects. Original basis: posttran-sonnet.pdf pp.3-4 defines business rejects and WARNING/4, but no return code or publication policy for malformed decoded inputs or arithmetic failures. |
| **persistence-and-restart:** This pure calculation neither persists checkpoints, prevents duplicate external writes, nor resumes partway through a run. Reusing identical snapshots and the same timestamp recalculates identical financial results without incrementing the input snapshots in place. | The documented persistence proposal is outside this calculation's delivery boundary; durable guarantees are not asserted. Original basis: posttran-sonnet.pdf pp.3-4 proposes per-transaction persistence and restart without duplicates; the maker left the persistence/file connection for later, so those durable guarantees are not claimed. |
| **infrastructure-failures:** The calculation does not simulate account rewrites, external retries, or reason-109 rejections. Any later persistence integration must address its own write failures without publishing partially updated state. | The cited external-write failure handling does not imply that this calculation performs those writes. Original basis: posttran-sonnet.pdf p.3 BR-08 says account rewrite failure 109 aborts a record and is not written to rejects; pp.17,19,21,23 describe external failure handling. This calculation has no such writes. |
| **reject-image:** Rejected output contains the original decoded transaction fields, an integer reason, and unpadded reason text. It does not reconstruct either the 350-byte transaction image or the 430-byte reject record. | The JSON representation uses the cited alternative to the legacy byte image and trailer. Original basis: posttran-sonnet.pdf p.3 BR-06 describes the legacy image and trailer; p.27 explicitly accepts JSON fields instead and permits omission of trailing spaces. |
| **assumptions-drafting:** The documented drafting process uses a model to write each assumption and wiki basis solely from this ledger; financial calculations never consume the model's answers. Missing, duplicate, or structurally incomplete drafting triggers fallback to the full authoritative ledger, which the process always appends as the definitive decision record. | This is the confirmed documentation process, not a wiki-prescribed drafting method; the ledger remains authoritative. Original basis: Maker requested every implementation decision and its wiki statement or absence. The confirmed description uses a separate model drafting step and deterministic fallback; the wiki prescribes no assumptions-document drafting method. |
