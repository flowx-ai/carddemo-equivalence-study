# Daily transaction posting assumptions

| What you assumed | Which wiki statement (or absence of one) it rests on |
|---|---|
| **delivery-scope:** The calculation accepts decoded records and supplies result arrays and assumptions text rather than physical files. Physical-file delivery requires a separate connection. | The recorded choice separates calculation delivery from the wiki’s file interface. Original basis: posttran-sonnet.pdf p.27 specifies file inputs and outputs. Maker explicitly chose calculation results and assumptions text without that connection. |
| **input-layouts:** Decoded input arrays follow the contract’s field names; fixed-width positions, filler bytes, and signed-overpunch decoding are not inferred. | The cited copybook references do not establish complete byte layouts. Original basis: posttran-sonnet.pdf pp.7,9-12,27 reference copybooks and lengths but do not supply complete byte layouts. |
| **required-arrays:** Each of the four input arrays must be explicitly present. Empty arrays are acceptable, but an omitted array causes a batch error rather than being interpreted as an empty file. | The explicit-presence requirement addresses behaviour absent from the cited input specification. Original basis: posttran-sonnet.pdf p.27 lists run inputs; behaviour for missing decoded input arrays is absent. |
| **money:** Amounts are handled as signed integer cents with safe-integer overflow checking. Values with more than two decimal places are rejected, and output amounts are JSON strings with exactly two decimal places, without rounding. | The decimal constraints are documented, while the arithmetic representation and rounding implementation are not. Original basis: posttran-sonnet.pdf pp.7,9-10 describes two-decimal amounts; p.27 allows strings or numbers with at most two decimals. Rounding and arithmetic implementation are unspecified. |
| **identity:** Supplied transaction identifiers remain unchanged. A repeated transaction ID anywhere in the feed, or a duplicate account, card-reference, or composite category-balance key, makes the whole calculation an error before any publishable updates. | The ledger resolves the differing ID descriptions and the absence of duplicate-input rules without introducing an ID sequence or transaction history. Original basis: posttran-sonnet.pdf p.3 proposes transaction-ID idempotency, while pp.9,23 propose generated IDs. p.27 supplies transaction IDs but no sequence or prior-transaction input. Duplicate input handling is unspecified. |
| **processing-time:** Unless a comparison timestamp is provided, one UTC processing timestamp is captured for the invocation. Its output format is YYYY-MM-DD HH:mm:ss.ffffff, with runtime milliseconds padded to six fractional digits. Rejected records retain their original timestamps. | The wiki specifies “now” and a timestamp length but leaves the clock conventions unspecified. Original basis: posttran-sonnet.pdf p.3 says processedTimestamp = now; pp.9-10 give a 26-character processed timestamp. Timezone, precision and a comparison clock are unspecified. |
| **business-date:** The default business date is 2022-07-18. Account expiry is compared with the transaction’s original calendar date rather than the business date, and an equal date is allowed. | The cited business date and strict expiry comparison support these distinct date roles. Original basis: posttran-sonnet.pdf p.27 fixes business date 2022-07-18; p.3 BR-04 uses account expiry < transaction original date. |
| **dependent-checks:** An absent card reference produces reason 100, with unavailable account checks skipped; an absent account produces reason 101. If an available account fails both limit and expiry checks, only reason 103 is retained. | The chosen dependency handling preserves the documented check order and overwrite rule while acknowledging the unresolved example. Original basis: posttran-sonnet.pdf pp.3-4 specifies xref then account then limit then expiry and last-reason overwrite, but p.4 also combines invalid card with expired account without explaining how that account is resolved. |
| **negative-debit:** For a posted negative amount, current cycle debit receives the signed negative value, not its absolute value. | This choice follows the stated signed addition rather than an alternative accounting-sign interpretation. Original basis: posttran-sonnet.pdf p.3 BR-05 explicitly says else currentCycleDebit += amount; alternative accounting-sign interpretations are not specified. |
| **zero-amount:** A transaction for zero posts when its reference, limit, and expiry checks pass. If its category balance does not exist, a zero category balance is created. | The ledger applies the documented nonnegative branch and missing-category creation, with no separate zero rule supplied. Original basis: posttran-sonnet.pdf p.3 BR-05 uses amount >= 0 and creates a missing category balance; it does not give a separate zero-amount rule. |
| **no-extra-validation:** Posting is decided only by the four documented business checks. Inactive status, missing type/category reference data, customer or card attributes, and the unused interest parameter are not independent grounds for rejection. | The additional inputs and parameter are not assigned further POSTTRAN business checks in the cited material. Original basis: posttran-sonnet.pdf pp.3-4 lists posting business checks; p.27 lists additional chain input files and the INTCALC parameter but assigns no additional POSTTRAN check to them. |
| **representation:** Account and merchant IDs are nonnegative JSON integers, and transaction category codes are integers. Card numbers, transaction IDs, and type codes remain strings. Category-balance category codes are four-character, zero-padded strings. String trimming removes only trailing ASCII spaces. | The ledger records the representation choices, including the category-balance JSON type left unresolved by the wiki. Original basis: posttran-sonnet.pdf p.27 fixes account, merchant and transaction category integer types and permits omission of trailing spaces. p.10 calls category-balance category codes four-character strings; p.27 does not resolve their JSON type. |
| **optional-fields:** Omitted optional account reissue dates and ZIP values are output as empty strings. Otherwise, decoded records must contain every required contract field. Dates must be valid ISO calendar dates, and original timestamps must start with such a date. | Optionality is documented, but defaults and malformed-input treatment are recorded implementation choices. Original basis: posttran-sonnet.pdf p.7 marks reissue date and account ZIP optional; p.27 requires output fields. Defaults and malformed-input handling are unspecified. |
| **whole-snapshot:** Results include all supplied accounts and category balances, even those unchanged, in their supplied order. New category balances are appended in the order first posted. This ordering has no business significance. | Complete snapshots are required, while the wiki permits any result-object order. Original basis: posttran-sonnet.pdf p.27 requires every account and category balance after posting and permits result objects in any order. |
| **errors:** Malformed decoded records, duplicate keys, or unsafe arithmetic produce ERROR, a null return code, and no publishable output arrays. They do not become business rejects, and partially calculated balances are not exposed. | The ledger’s error and publication policy covers failure cases not assigned a policy by the cited business-reject rules. Original basis: posttran-sonnet.pdf pp.3-4 defines business rejects and WARNING/4, but no return code or publication policy for malformed decoded inputs or arithmetic failures. |
| **persistence-and-restart:** The pure calculation neither saves checkpoints nor prevents duplicate external writes, and it cannot resume midway. Reusing identical snapshots and the same timestamp recalculates identical financial results without incrementing the supplied snapshots in place. | The proposed durable persistence and restart behaviour is outside this calculation’s scope. Original basis: posttran-sonnet.pdf pp.3-4 proposes per-transaction persistence and restart without duplicates; the maker left the persistence/file connection for later, so those durable guarantees are not claimed. |
| **infrastructure-failures:** Account rewrites, external retries, and reason-109 rejections are not simulated. Any later persistence integration must address its own write failures without publishing partially updated state. | The external-write failure rules are acknowledged but not simulated by a calculation that performs no such writes. Original basis: posttran-sonnet.pdf p.3 BR-08 says account rewrite failure 109 aborts a record and is not written to rejects; pp.17,19,21,23 describe external failure handling. This calculation has no such writes. |
| **reject-image:** Reject output consists of the original decoded transaction fields, an integer reason, and reason text without padding. It does not reconstruct a 350-byte transaction image or a 430-byte reject record. | The accepted JSON representation replaces reconstruction of the cited legacy image and trailer. Original basis: posttran-sonnet.pdf p.3 BR-06 describes the legacy image and trailer; p.27 explicitly accepts JSON fields instead and permits omission of trailing spaces. |
| **assumptions-drafting:** A separate model drafts assumptions and wiki bases using only this ledger; its answers never drive financial calculations. Missing, duplicate, or structurally incomplete drafting triggers fallback to the complete authoritative ledger. The recorded process always appends that ledger as the definitive decision record. | This drafting and fallback process comes from the maker’s confirmed description, not a wiki-prescribed document method. Original basis: Maker requested every implementation decision and its wiki statement or absence. The confirmed description uses a separate model drafting step and deterministic fallback; the wiki prescribes no assumptions-document drafting method. |
