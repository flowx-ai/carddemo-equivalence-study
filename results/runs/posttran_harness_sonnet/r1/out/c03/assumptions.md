# Daily transaction posting assumptions

| What you assumed | Which wiki statement (or absence of one) it rests on |
|---|---|
| **delivery-scope:** The implementation accepts decoded records and returns result arrays and assumptions text rather than physical files. Physical-file delivery remains a separate connection. | The documented file interface is distinguished from the maker’s selected calculation-only scope. Original basis: posttran-sonnet.pdf p.27 specifies file inputs and outputs. Maker explicitly chose calculation results and assumptions text without that connection. |
| **input-layouts:** Decoded input arrays follow the contract’s field names. The implementation does not guess fixed-width field offsets, filler bytes, or signed-overpunch decoding. | The referenced copybooks and lengths do not establish complete byte layouts. Original basis: posttran-sonnet.pdf pp.7,9-12,27 reference copybooks and lengths but do not supply complete byte layouts. |
| **required-arrays:** Each of the four input arrays must be explicitly present. Empty arrays are accepted, but an omitted array causes a batch error rather than being interpreted as an empty file. | Required run inputs are documented; the missing-array error policy is an implementation choice where decoded-array behaviour is absent. Original basis: posttran-sonnet.pdf p.27 lists run inputs; behaviour for missing decoded input arrays is absent. |
| **money:** Monetary arithmetic uses signed integer cents and checks for safe-integer overflow. Values with more than two decimal places are rejected; output amounts are two-decimal JSON strings, with no rounding. | The decimal constraints are documented, while rounding and arithmetic mechanics are not. Original basis: posttran-sonnet.pdf pp.7,9-10 describes two-decimal amounts; p.27 allows strings or numbers with at most two decimals. Rounding and arithmetic implementation are unspecified. |
| **identity:** Supplied transaction IDs remain unchanged. Any repeated transaction ID anywhere in the feed, or any duplicate account key, card-reference key, or composite category-balance key, makes the whole calculation an error before updates can be published. | Conflicting ID proposals and absent duplicate-input rules underpin the ledger’s identity choice. Original basis: posttran-sonnet.pdf p.3 proposes transaction-ID idempotency, while pp.9,23 propose generated IDs. p.27 supplies transaction IDs but no sequence or prior-transaction input. Duplicate input handling is unspecified. |
| **processing-time:** Unless a comparison timestamp is supplied, one UTC processing time is captured for the invocation. Its output format is YYYY-MM-DD HH:mm:ss.ffffff, with runtime milliseconds padded to six fractional digits. Rejected records retain their original timestamps. | The wiki supplies a current-time instruction and timestamp length, but leaves clock details unspecified. Original basis: posttran-sonnet.pdf p.3 says processedTimestamp = now; pp.9-10 give a 26-character processed timestamp. Timezone, precision and a comparison clock are unspecified. |
| **business-date:** The default business date is 2022-07-18. Expiry is compared with the original transaction’s calendar date, not the business date, and an equal expiry date is allowed. | The fixed business date and strict expiry comparison support this distinction. Original basis: posttran-sonnet.pdf p.27 fixes business date 2022-07-18; p.3 BR-04 uses account expiry < transaction original date. |
| **dependent-checks:** If the card reference is missing, reason 100 is returned without trying account checks whose data is unavailable. A missing account produces 101. For an available account that fails both limit and expiry checks, only reason 103 is retained. | The ordered checks and overwrite rule are documented, alongside an unresolved invalid-card example. Original basis: posttran-sonnet.pdf pp.3-4 specifies xref then account then limit then expiry and last-reason overwrite, but p.4 also combines invalid card with expired account without explaining how that account is resolved. |
| **negative-debit:** When a posted amount is negative, that signed negative amount is added to current cycle debit; its absolute value is not substituted. | The ledger follows the stated signed addition rather than an alternative sign interpretation. Original basis: posttran-sonnet.pdf p.3 BR-05 explicitly says else currentCycleDebit += amount; alternative accounting-sign interpretations are not specified. |
| **zero-amount:** A transaction for zero is posted when its reference, limit, and expiry checks succeed. If its category balance does not exist, a zero category balance is created. | The existing nonnegative-amount branch and missing-category rule are the basis; no separate zero rule is documented. Original basis: posttran-sonnet.pdf p.3 BR-05 uses amount >= 0 and creates a missing category balance; it does not give a separate zero-amount rule. |
| **no-extra-validation:** Posting is decided only by the four documented business checks. Inactive status, missing type/category reference data, customer/card attributes, or the unused interest parameter do not by themselves cause rejection. | Additional chain inputs and the interest parameter are not assigned additional POSTTRAN checks. Original basis: posttran-sonnet.pdf pp.3-4 lists posting business checks; p.27 lists additional chain input files and the INTCALC parameter but assigns no additional POSTTRAN check to them. |
| **representation:** Account and merchant IDs are nonnegative JSON integers, and transaction category codes are integers. Card numbers and transaction IDs remain strings. Category-balance category codes are four-character, zero-padded strings; type codes remain strings. String trimming removes only trailing ASCII spaces. | The contract documents some types and trailing-space omission, but does not resolve the category-balance JSON type. Original basis: posttran-sonnet.pdf p.27 fixes account, merchant and transaction category integer types and permits omission of trailing spaces. p.10 calls category-balance category codes four-character strings; p.27 does not resolve their JSON type. |
| **optional-fields:** An omitted optional account reissue date or ZIP is returned as an empty string. All other required contract fields must be present in decoded records. Dates must be valid ISO calendar dates, and original timestamps must start with a valid date of that form. | Optionality and required output fields are documented; defaults and malformed-input treatment are not. Original basis: posttran-sonnet.pdf p.7 marks reissue date and account ZIP optional; p.27 requires output fields. Defaults and malformed-input handling are unspecified. |
| **whole-snapshot:** Output includes all supplied accounts and category balances, even unchanged rows, in their supplied order. New category balances are appended in first-posted order. This ordering has no business significance. | Complete snapshots are required, while the chosen ordering is permitted rather than prescribed. Original basis: posttran-sonnet.pdf p.27 requires every account and category balance after posting and permits result objects in any order. |
| **errors:** Malformed decoded records, duplicate keys, or unsafe arithmetic produce ERROR, a null return code, and no publishable output arrays. Such failures are not turned into business rejects, and partially calculated balances are not exposed. | The business-reject outcome is documented, but the technical-error return code and publication policy are not. Original basis: posttran-sonnet.pdf pp.3-4 defines business rejects and WARNING/4, but no return code or publication policy for malformed decoded inputs or arithmetic failures. |
| **persistence-and-restart:** The pure calculation provides no persisted checkpoints, duplicate-external-write prevention, or midway resumption. Reusing the same snapshots and timestamp recalculates the same financial results without incrementing the supplied snapshots in place. | Proposed durable behaviour is outside the calculation’s deferred persistence/file connection. Original basis: posttran-sonnet.pdf pp.3-4 proposes per-transaction persistence and restart without duplicates; the maker left the persistence/file connection for later, so those durable guarantees are not claimed. |
| **infrastructure-failures:** The calculation does not simulate account rewrites, external retries, or reason-109 rejections. Any later persistence integration must manage its own write failures without publishing partially updated state. | External write-failure provisions are documented but do not represent writes performed by this calculation. Original basis: posttran-sonnet.pdf p.3 BR-08 says account rewrite failure 109 aborts a record and is not written to rejects; pp.17,19,21,23 describe external failure handling. This calculation has no such writes. |
| **reject-image:** Reject output retains the original decoded transaction fields and adds an integer reason with unpadded reason text. It does not reconstruct either the 350-byte legacy image or the 430-byte reject record. | The accepted JSON representation replaces reconstruction of the documented legacy image and trailer. Original basis: posttran-sonnet.pdf p.3 BR-06 describes the legacy image and trailer; p.27 explicitly accepts JSON fields instead and permits omission of trailing spaces. |
| **assumptions-drafting:** The ledger’s drafting design uses a model to separately draft each assumption and wiki basis solely from the ledger; financial calculations never consume those answers. Missing, duplicate, or structurally incomplete drafting triggers fallback to the full authoritative ledger. Under that design, the ledger is always appended as the definitive decision record. | This drafting and fallback design comes from the maker’s confirmed description, not a wiki-prescribed documentation method. Original basis: Maker requested every implementation decision and its wiki statement or absence. The confirmed description uses a separate model drafting step and deterministic fallback; the wiki prescribes no assumptions-document drafting method. |
