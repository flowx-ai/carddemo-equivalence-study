# Assumption ledger (extracted verbatim from the Calculate posting script)

1. **assumption**: Decoded records are supplied and all results, including the assumptions document, are returned as data only. | **source**: posttran-sonnet.pdf p.27; maker scope answer | **rationale**: CONTRACT.md requests files. The maker accepted excluding fixed-width file reading and JSON/Markdown file writing; no output files are created.
2. **assumption**: Only POSTTRAN is calculated; unrelated reference files and INTCALC are not used. | **source**: posttran-sonnet.pdf pp.3,27 | **rationale**: Posting rules use the daily feed, accounts, card cross-references and category balances. No posting rule uses disclosure, customer, card, type or category reference files.
3. **assumption**: Process feed records sequentially against balances updated by earlier accepted records. | **source**: posttran-sonnet.pdf p.2 | **rationale**: The specification describes one iteration per record and replacement of the legacy sequential read loop.
4. **assumption**: Missing card gives 100 and stops lookup; missing linked account gives 101. Limit is checked before expiry; expiry overrides limit. Expiry on the original transaction date is allowed. | **source**: posttran-sonnet.pdf pp.3-4 | **rationale**: Ordered lookups are explicit; the invalid-card plus expired-account example provides no account to inspect when the card lookup fails. Strictly less-than expiry is specified.
5. **assumption**: Do not add active-status, type or category-reference validation. | **source**: posttran-sonnet.pdf pp.3-4 | **rationale**: No such rejection rule is listed; retain only reasons 100-103.
6. **assumption**: Use exact integer cents and emit amounts as strings with exactly two decimal places. Reject malformed or unsafe numeric input without partial results. | **source**: posttran-sonnet.pdf pp.7,9-10,27 | **rationale**: Two-decimal amounts are specified; malformed input and arithmetic overflow handling are not specified. Never round an amount having more than two decimals.
7. **assumption**: For accepted amounts greater than or equal to zero increment cycle credit; for negative amounts increment cycle debit by the negative amount, not its absolute value. | **source**: posttran-sonnet.pdf p.3 BR-05 | **rationale**: Preserve the documented sign even though the limit formula subtracts the resulting negative cycle debit.
8. **assumption**: Compare the original calendar date to account expiry without timezone conversion. Use a supplied processingTimestamp; if absent use businessDate at midnight, default business date 2022-07-18. | **source**: posttran-sonnet.pdf pp.3,27 | **rationale**: The wiki says now without specifying timezone or a reproducible clock; the contract fixes business date 2022-07-18. Midnight is an explicit deterministic default, not an observed legacy timestamp.
9. **assumption**: Preserve supplied transaction identifiers. Duplicate transaction identifiers in the feed fail the invocation rather than post twice or silently disappear. | **source**: posttran-sonnet.pdf pp.3,9,23,27 | **rationale**: The wiki describes transactionId idempotency and sequence allocation but supplies no sequence seed or duplicate-feed resolution. Preserve identifiers for comparison and refuse ambiguous duplicates.
10. **assumption**: Replay of original input snapshots and timestamp yields identical financial results but is not a durable resume. There are no store failures or reason 109 in this calculation. | **source**: posttran-sonnet.pdf p.3 BR-08 and BR-09 | **rationale**: Persistent posting, checkpoints and restart were excluded with file handling. Reason 109 is an account rewrite failure, not a business reject.
11. **assumption**: Missing input lists mean empty lists. Empty feeds return every supplied account and category balance unchanged in value; malformed records or duplicate master keys fail the whole invocation with empty result lists. | **source**: posttran-sonnet.pdf pp.5,19,27; absence of malformed-record policy | **rationale**: Empty feed handling is described as NO_DATA. The contract requires all accounts and category balances. No malformed decoded-record or duplicate master-key policy is defined.
12. **assumption**: Trim trailing spaces in text; normalize numeric account, merchant and category identifiers for comparison and output. Keep card numbers as strings. Category-balance category codes are returned as integers. | **source**: posttran-sonnet.pdf pp.7,9-10,27 | **rationale**: Trailing spaces may be omitted; account and transaction numeric fields are specified. The category-balance table does not separately spell out identifier types, so use the corresponding numeric contract identities.
13. **assumption**: Return business rejects with original transaction fields and timestamps plus integer reason and unpadded description. Only accepted transactions replace processed timestamp. | **source**: posttran-sonnet.pdf pp.3,5,27 | **rationale**: The contract chooses structured JSON rather than the fixed-width original-image trailer; accepted processing timestamp is set by BR-05.
14. **assumption**: Malformed invocation has status ERROR and return code 8; otherwise any reject has WARNING and 4, no rejects has OK and 0. No partial financial results are returned on invalid invocation. | **source**: posttran-sonnet.pdf p.3 BR-07; absence of malformed-invocation return code | **rationale**: Warning code 4 is documented. Code 8 is an explicit calculation-interface error convention, not a claimed COBOL return code.
15. **assumption**: An isolated model writes the assumptions explanation from this ledger and the supplied wiki excerpts; its output cannot change financial results. On failure label the explanation unavailable and return the complete raw ledger. | **source**: maker confirmed description; absence of explanatory-model behaviour in wiki | **rationale**: This is implementation documentation, not a legacy posting rule. Only the ledger is sent to the model, never account or transaction records.
