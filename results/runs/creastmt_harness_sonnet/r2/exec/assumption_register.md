# Assumption ledger (extracted verbatim from the workflow scripts' decision() calls)

1. **input-layout-account**: Infer contiguous account fields: ID [0,11), status [11,12), balance [12,24), credit limit [24,36), cash limit [36,48), dates [48,78), cycle credit/debit [78,102), ZIP [102,112), group [112,122), filler [122,300); offsets are zero-based and unverified against original copybooks. _Basis:_ The Account table lists these widths and order and says Legacy FILLER (178 bytes) is dropped; the original copybook is not supplied. p.6
2. **input-layout-customer**: Treat CUSTREC as the listed CVCUS01Y layout: ID [0,9), first/middle/last [9,34),[34,59),[59,84), addresses [84,134),[134,184),[184,234), state [234,236), country [236,239), ZIP [239,249), phones [249,279), SSN [279,288), government ID [288,308), DOB [308,318), EFT [318,328), primary flag [328,329), FICO [329,332), remaining filler to 500; this is not verified copybook compatibility. _Basis:_ Customer table names CVCUS01Y and lists ordered field widths; the statement input contract instead names CUSTREC, without resolving that identity or supplying original offsets. pp.7,26
3. **input-layout-xref**: Infer cross-reference card [0,16), customer [16,25), account [25,36), filler [36,50). _Basis:_ CardXref lists cardNumber String(16), customerId String(9), accountId String(11); CONTRACT.md specifies a 50-character record, not original copybook offsets. pp.8,26
4. **input-layout-transaction**: Infer transaction ID [0,16), type [16,18), category [18,22), source [22,32), description [32,132), amount [132,143), merchant ID [143,152), merchant name [152,202), city [202,252), ZIP [252,262), card [262,278), timestamps [278,304),[304,330), filler [330,350). _Basis:_ The Transaction table gives these field widths and order; CONTRACT.md names CVTRA05Y and 350 characters but does not supply the original layout. pp.8-9,26
5. **file-envelope**: Accept all four file contents as strings under files, return named line arrays and assumptions.md in one result, and do not create disk files. _Basis:_ The contract permits a list of strings under the output filename without its extension; the maker selected content-input and returned-output delivery. p.26
6. **record-encoding**: Inputs are decoded ASCII-compatible strings; accept LF or CRLF and one optional final newline, reject non-ASCII characters, bare CR, internal blank records and wrong record lengths; empty but present files contain zero records. _Basis:_ CONTRACT.md says fixed-width text, one record per line, and specifies 350/300/50/500; text encoding, newline details and empty-file handling are otherwise silent. p.26
7. **money-decoding**: Decode signed implied-decimal cents as unsigned digits or uppercase ASCII COBOL trailing overpunch ({ABCDEFGHI positive, }JKLMNOPQR negative); reject other encodings, use safe integer cents and canonicalize negative zero. _Basis:_ Account pictures are S9(10)V99 and transaction amount S9(9)V99; the wiki does not define the input-file sign encoding. pp.6,8
8. **identifier-display**: Require numeric identifiers at their declared widths, preserve leading zeros in account/card/customer IDs, and print all three FICO characters (blank FICO prints blank); do not impose online active-status or FICO-range validation on statement input. _Basis:_ IDs are numeric fixed-width strings and FICO is 9(3) in the data tables; printed account and FICO use X(20), without a de-zeroing or range-validation rule for this batch. pp.6-8,27
9. **selection**: Emit one statement per cross-reference sorted by card number; use only transactions with that exact card number, sorted by transaction ID, including all dates and statuses; transactions without a cross-reference are not selected, and unused account/customer rows produce no statement. _Basis:_ BR-01: Statement driven by CardXref order (card number); BR-02: Transactions are keyed by card number + transaction id; p.3 says legacy prints all transactions on file, with cycle filtering still a TODO. pp.2-3
10. **account-sharing**: Cards sharing an account get separate statements containing only their own transactions, not the combined transactions of sibling cards. _Basis:_ The process loops For Each Card and calls GET_STATEMENT_DATA {cardNumber}; acceptance says One statement per card, while the plugin also uses the less precise phrase per card of the account. pp.2,4,21
11. **duplicates-and-missing**: Fail the whole run for duplicate account/customer/card-cross-reference keys, duplicate card+transaction-ID keys, blank transaction IDs, missing referenced account/customer, invalid numeric syntax or unrepresentable money; never skip bad records or return partial statements. _Basis:_ The wiki identifies primary keys and joins, but gives no statement-specific malformed-record recovery; batch chain BR-02 says A failing step stops the chain. pp.6-8,13,23
12. **name-assembly**: Trim field-edge spaces and join nonblank first, middle and last names with one space, preserving spaces inside each component; truncate the assembled name to 75 characters for text. _Basis:_ Customer fields are firstName, middleName and lastName; the contract gives customer name X(75) but no joining rule. pp.7,27
13. **address-assembly**: Trim address fields; print customer addressLine1 and addressLine2 separately; join nonblank addressLine3, state and ZIP with one space for final address line, omitting country; do not add phone or SSN. _Basis:_ The plugin requires name, address (3 lines, state, zip), phone and states SSN is not printed; the controlling layout has exactly three address lines and no phone or country slot, and does not specify assembly. pp.7,21,27-28
14. **fixed-pictures**: Use exactly nine integer digits plus point, two fractional digits and trailing minus/space in 13 columns; balance retains leading zeros, detail and total replace leading integer zeros with spaces (zero is nine spaces plus .00 and trailing space); reject magnitudes above 999999999.99 or unsafe integer sums. _Basis:_ CONTRACT.md defines 9(9).99- and Z(9).99- and fixes the 13-column positions; it does not state how overflow is handled. p.27
15. **text-layout**: Use the supplied literal lines and repeated separators, right-pad each line to 80, truncate description to its X(49) slot, pad the column-heading line to 80, concatenate statements without blank lines or page breaks, and produce zero-total statements even with no transactions. _Basis:_ CONTRACT.md gives the printed line order and permits omitted trailing spaces; acceptance says Card without transactions: Statement with zero total, but does not specify inter-statement separators or long-field policy. pp.4,27
16. **html-layout**: Use the literal HTML lines without added indentation, preserve specified X(20)/X(16)/X(49) field padding inside tags, use trimmed assembled name/address values for unspecified-width insertions, HTML-escape field values, then pad lines to 100; reject an insertion whose escaped line exceeds 100 rather than corrupt markup. _Basis:_ CONTRACT.md supplies fixed HTML lines and explicit pictures for some insertions but no escaping, indentation or oversized-insertion policy. pp.27-29
17. **html-documents-and-totals**: Concatenate a complete HTML document for each card in cross-reference order; use its closing block even for zero transactions, and do not invent an HTML total block or extra phone/date/credit-limit fields. _Basis:_ The contract specifies one statement with a transaction block and closing block; unlike text it has no total line, despite the broader plugin content description. pp.21,27-29
18. **assumptions-drafting**: Use a model only to explain this authoritative ledger, with no input records or statements; require one entry per decision, exact preservation of its assumption and source, and nonblank explanation; on drafting failure return an error and authoritative Markdown ledger, without statements. _Basis:_ The maker requires each decision and its wiki basis in assumptions.md; the wiki is silent about how that ledger is written or failures during its drafting. pp.2-4,21,26
19. **testing-limit**: Synthetic tests use the inferred layouts, not observed legacy files, and independently expected printed lines must come from the contract; no oracle-equivalence claim is made. _Basis:_ The contract describes comparison to an oracle and step isolation, but the attachment contains no oracle runs, original copybooks or input datasets. pp.25-26
