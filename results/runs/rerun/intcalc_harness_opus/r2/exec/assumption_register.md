# Assumption ledger (extracted verbatim from the workflow scripts' entry() calls)

1. **calculation**: Calculate once per account using its current balance multiplied by the matching group rate; do not calculate separate interest for each category. _Basis:_ P.2 states interest = currentBalance × interestRate(groupId) and explicitly leaves exact formula and grouping as TODO. p.2
2. **rate-units**: Interpret the supplied rate as a decimal multiplier without division by 100, annualisation or proration; permit signed rates. _Basis:_ The wiki specifies a group rate but gives neither units, day-count basis nor sign restriction. pp.2,4
3. **group-match**: Remove trailing spaces from group identifiers and require exactly one matching rate, including for a zero-balance account; do not use a default rate. _Basis:_ Disclosure-group lookup is stated; whitespace, duplicate and missing-rate behaviour are not. p.2
4. **rounding**: Use exact decimal arithmetic and round the interest product once to cents, half away from zero. _Basis:_ The rounding boundary scenario says TODO: confirm rounding mode. p.4
5. **eligibility**: Process inactive accounts and negative balances as well as active accounts and positive balances. _Basis:_ The flow says for each account; no eligibility restriction is stated. p.2
6. **account-posting**: Add rounded interest to current balance and preserve every other account field, including cycle debit and credit totals. _Basis:_ Post Interest says add interest to balance; cycle-counter changes are not specified. pp.2,5,6
7. **category-posting**: Add the same nonzero rounded interest to the account category with type IN and category 0; create that category when absent. _Basis:_ Interest is posted to balance and category balance, but no destination codes or missing-category rule are specified. p.2
8. **category-result**: Return updated category balances as a supplementary dataset, not as another contracted output file. _Basis:_ The wiki calls for category posting, while the INTCALC contract lists only transaction and account output files. pp.2,10,11
9. **zero-interest**: When rounded interest is zero, leave balances unchanged and emit neither a transaction nor a new category. _Basis:_ The zero-balance scenario requires zero interest but does not specify whether a zero-value transaction is written. p.4
10. **transaction-fields**: For interest transactions use type IN, category 0, source INTCALC, description Interest, merchant identifier 0 and empty merchant name, city and ZIP. _Basis:_ The contract names transaction fields and types but gives no interest-specific metadata values. p.10
11. **transaction-id**: Construct the 16-character transaction identifier from the ten-digit run parameter plus the six-digit one-based account input position, counting unsuccessful and zero-interest accounts too. _Basis:_ The parameter is supplied and a 16-character transaction identifier is described; construction and sequencing are absent. pp.7,10
12. **card-selection**: Choose the lexicographically first matching card number after removing trailing spaces; use an empty string if none. Numeric card numbers are not reconstructed because leading zeros may already be lost. _Basis:_ Card links and card-number fields are described but interest-specific selection and missing-card behaviour are absent. pp.7,8,10
13. **timestamps**: Set both timestamps to business-date midnight as YYYY-MM-DD 00:00:00.000000. _Basis:_ Timestamp fields and run business date are provided without an interest-specific timestamp rule. pp.8,10
14. **account-errors**: For missing or ambiguous rates, duplicate account identifiers, ambiguous target categories, invalid values read by calculation or unrepresentable computed amounts, retain the account unchanged, report an error and make no partial posting; continue other accounts. _Basis:_ The wiki does not specify record-level failure handling. pp.2,4
15. **representations**: Accept decoded decimal strings or finite JSON numbers, including exponent notation; preserve digit identifiers as strings internally and card numbers as strings. Convert account identifiers to integers only at the output boundary. Ignore fields not used by this calculation. _Basis:_ The model describes digit identifiers and signed decimal money; the output contract requires integer account identifiers and allows string or numeric amounts. pp.5,6,7,8,10,11
16. **numeric-capacity**: Require current account and target-category balances to have whole cents; enforce the documented account, category and transaction money capacities before committing a posting. _Basis:_ The data model gives account decimal(12,2), category decimal(11,2) and transaction decimal(11,2) layouts; overflow handling is not specified. pp.5,8
17. **batch-boundaries**: Omitted record lists mean empty lists. Wrong list shapes, invalid account identity, invalid run date or a run parameter other than ten digits invalidate the batch before posting. Require complete decoded account records from the caller, without validating unused dates or filler fields. _Basis:_ The contract describes per-run files and parameters but no decoded API or malformed-batch policy. pp.10,11
18. **run-defaults**: Use business date 2022-07-18 and parameter 2022071800 when omitted. Each invocation applies one cycle to its supplied snapshot without replay protection. _Basis:_ These run values and step isolation are given; replay and execution-history rules are absent. p.10
19. **explanation**: Draft the explanation only from this ledger and verified excerpts. Validate exact ledger coverage, behaviour and source references; use the complete fixed ledger and Markdown table if drafting fails validation. A model never changes financial results. _Basis:_ This is an implementation convention for the maker-requested assumptions text, not a legacy financial rule. pp.2,4,10
