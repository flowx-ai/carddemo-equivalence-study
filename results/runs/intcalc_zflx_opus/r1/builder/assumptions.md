# INTCALC (interest calculation): assumptions and decisions

These are the places where the wiki pages (`process-interest-calculation.md`,
`acceptance-criteria-interest-calculation.md`, `project-data-model.md`) and
CONTRACT.md are uncertain, incomplete or silent, and how this build decided. Code
references point to `src/intcalc_core.py`, which is also the code of the FlowX
SCRIPT node. Comments tagged `(A<n>)` in the code point to the entries below.

**A note on sources.** The wiki leaves the formula open:
`{{TODO: Extract exact interest formula, rounding, and grouping from CBACT04C + DISCGRP.}}`.
The acceptance criteria require "matches legacy" and "identical per account".
I filled that gap from the public AWS CardDemo source of `CBACT04C`, as I
remember it. That code was **not** among the supplied material, so every rule
below marked *legacy* comes from outside the wiki. It could be wrong, and it is a
decision, not a documented fact.

| # | Topic | Decision | Wiki basis |
|---|-------|----------|------------|
| A1 | Authority for the formula | Behaviour follows legacy `CBACT04C` wherever the wiki defers to it or is silent. | Process page: "Rule: ComputeInterest … `{{TODO: Extract exact interest formula, rounding, and grouping from CBACT04C + DISCGRP.}}`". Acceptance criteria #1: "matches legacy"; Legacy Comparison: "identical per account". |
| A2 | What interest is computed on, and the formula | Interest is computed **per transaction-category balance** (each TCATBAL record), not once per account on `currentBalance`. The rate is looked up in DISCGRP by key (account `group_id`, the record's `type_cd`, the record's `cat_cd`). `monthly interest = TRAN-CAT-BAL × DIS-INT-RATE / 1200`: the rate is an annual percentage, applied monthly. The account's interest is the sum over its categories. | The wiki says `interest = currentBalance × interestRate(groupId)`, "rate per account group", "balance × rate(groupId)". It also lists `TransactionCategoryBalance` as related data ("Used by: … Interest Calculation"), and the contract supplies `tcatbal.dat` / `discgrp.dat` (CVTRA02Y has type/category key parts) as inputs. Taken literally, the wiki formula would ignore the category balances and the DISCGRP key structure. I followed legacy (A1). |
| A3 | Rounding | Each category's interest is **truncated toward zero** to cents (COBOL `COMPUTE` without `ROUNDED`). Example: 15.432 → 15.43, −3.134 → −3.13. All arithmetic uses integer cents, with no floating point. | Acceptance criteria #2: "Rounding matches legacy `{{TODO: confirm rounding mode}}`". |
| A4 | Posting to the account | When processing moves to the next account, the account just finished gets `curr_bal += total interest`, and `curr_cyc_credit` and `curr_cyc_debit` are set to **0** (legacy 1050-UPDATE-ACCOUNT). Accounts without TCATBAL records are left unchanged. **The last account in TCATBAL order is not rewritten**: in legacy, the EOF branch that would update it is unreachable inside `PERFORM UNTIL END-OF-FILE = 'Y'`. Its interest transactions are still written. I reproduced this so the result is "identical per account" to legacy. `--post-last-account` (runner) / `postLastAccount: true` (workflow input) switches to the literal wiki reading, and the account is flagged in `flags.json`. | Process page: "posts the interest to the account"; node "Post Interest – Add interest to balance"; "posted to balance and category balance". The wiki never mentions resetting the cycle totals or the last-account behaviour. |
| A5 | Category balance after posting | Category balances are **not** updated with the interest, and no TCATBAL output is produced. | Rule: "posted to balance and category balance". Legacy CBACT04C does not rewrite TCATBAL, and CONTRACT.md lists no INTCALC category-balance output. |
| A6 | Missing group rate, zero rate, zero balance | If there is no DISCGRP record for (group, type, category), the `DEFAULT` group is used (legacy). A rate of 0 means no interest and **no transaction**. A zero balance with a non-zero rate gives interest 0.00, and a 0.00 interest transaction **is** written (legacy). | Acceptance criteria #3: "Account balance 0 → Zero interest" (satisfied: amount 0.00). #4: "Correct rate per group". The fallback group and the zero-rate case are not in the wiki. |
| A7 | Processing order and transaction ids | TCATBAL is processed in ascending key order (account, type, category), as a sequential read of the KSDS would do. The input is sorted, so file order does not matter. `tran_id` = INTCALC parameter (10 chars, `2022071800`) + a 6-digit sequence starting at `000001`, in that processing order. | Process: "For each account … More?" loop. Transaction ids are not described. |
| A8 | Interest transaction fields | `type_cd "01"`, `cat_cd 5`, `source "System"`, `desc "Int. for a/c " + 11-digit zero-padded account id`, `amt` = that category's interest, `merchant_id 0`, merchant name/city/zip blank, and `card_num` from the card cross-reference (A9). These are legacy values. | The wiki does not mention the interest *transaction* (SYSTRAN) at all. CONTRACT.md fixes only the field names (`intcalc_systran.json`). |
| A9 | Card number for the transaction | The first `cardxref.dat` record (in file order) whose account id matches. This stands in for the legacy read via the account alternate index. | Not in the wiki. The data model notes "CardXref … alternate index on accountId". |
| A10 | Timestamps (`orig_ts`, `proc_ts`) | `<business date>-00.00.00.000000`, i.e. `2022-07-18-00.00.00.000000`, in the legacy DB2 timestamp layout. Legacy reads the system clock, so these values cannot be reproduced exactly. I chose a deterministic value based on the contract's business date. | Not in the wiki. CONTRACT.md gives "business date 2022-07-18". |
| A11 | Overflow | High-order digits are dropped as in COBOL fields without `ON SIZE ERROR`: monthly and total interest S9(9)V99, account balance S9(10)V99. In practice this is never reached. | Data model gives the field sizes only. |
| A12 | Missing reference data | Legacy abends (stops) here. This build carries on, reports a warning, and lists it in `flags.json`. An account in TCATBAL but not in the account file gets no update, and the previous account's group is used for its rate. A missing card xref gives a blank `card_num`. If the DEFAULT rate is also missing, the rate is 0. A duplicate DISCGRP key keeps the first record (as a KSDS load would). A duplicate account id: the first record is the one updated. | Not in the wiki. |
| A13 | Which account / category-balance files to read | The runner prefers `posttran_acctdata.*` / `posttran_tcatbal.*` (fixed-width `.txt`/`.dat`, or `.json`) if present in the input directory. Otherwise it reads `acctdata.dat` / `tcatbal.dat`. Explicit `--acctdata` / `--tcatbal` override both. | CONTRACT.md: "A candidate for INTCALC receives the oracle's POSTTRAN outputs as its account and category-balance inputs". The file name/form is not stated. |
| A14 | Input record parsing | Fixed width per copybook: CVACT01Y 300, CVTRA01Y 50, CVTRA02Y 50, CVACT03Y 50. Short lines (trailing spaces trimmed) are padded, blank lines ignored, and files read as Latin-1. Signed zoned fields accept overpunch `{A–I` (+), `}J–R` (−), GnuCOBOL ASCII `p–y` (−), and plain digits or a separate leading/trailing sign. | CONTRACT.md: "fixed width, layouts as in the copybooks". The data model: "Packed/zoned/signed numerics … map to NUMBER". The sign encoding is not stated. |
| A15 | Output content and format | `intcalc_acctdata.json` lists **every** input account in input order, changed or not. `intcalc_systran.json` lists every interest transaction written. Amounts are strings with exactly 2 decimals (`"-3.13"`); `acct_id`, `cat_cd` and `merchant_id` are ints; other strings have trailing spaces removed. | CONTRACT.md: "account fields for every account, after interest"; "transaction fields for every interest transaction written". |
| A16 | Account status | Interest is computed for every account in TCATBAL, whatever its `active_status` (legacy does not check it). | The wiki does not mention status. |
| A17 | Fees | Not implemented. The legacy 1400-COMPUTE-FEES paragraph is an empty stub. | The wiki mentions only interest. |
| A18 | FlowX shape | The step is built as one FlowX integration workflow `intcalc_batch` (START → SCRIPT "Compute Interest" (Python) → END). The file contents are passed in and both outputs come back as typed arrays. The wiki's BPMN shape is **not** built: scheduled start, "Load Accounts"/"Save Account" Kafka send/receive against `ai.flowx.in.carddemo.datastore.*` / FlowX Persistence, and a per-account loop. No datastore service exists for those topics, and the contract is file-in/file-out. Accounts are loaded, computed and "saved" (returned) inside the one script, in the same per-account order. No schedule trigger is configured. | Process page: Nodes 1–6 and Integration Touchpoints. CONTRACT.md defines files as the interface. |
| A19 | Run parameters | INTCALC parameter `2022071800` → `parmDate`; business date `2022-07-18` → `businessDate`. Both are the defaults, and both can be overridden. | CONTRACT.md "Run parameters". |
