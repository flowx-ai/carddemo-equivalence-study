# Assumption ledger (extracted verbatim from the build script's `decisions` array: title, assumption, basis, note)

1. **A01 Delivery**: Accept decoded fixed-width file contents in files, keyed by transact.dat, cardxref.dat, trantype.dat and trancatg.dat. Return report lines under tranrept_report and assumptions.md beside them within dailyTransactionReport, not physical disk files. _Basis:_ CONTRACT.md, pp.16-17 explicitly permits returned lines instead of a file; no storage connection is supplied. The caller supplies contents and may save the returned artifacts.
2. **A02 Transaction layout**: Use 1-based inclusive offsets: transaction ID 1-16; type 17-18; category 19-22; source 23-32; description 33-132; amount 133-143; merchant ID 144-152; merchant name 153-202; merchant city 203-252; merchant ZIP 253-262; card number 263-278; origin timestamp 279-304; processing timestamp 305-330; filler 331-350. _Basis:_ Project Data Model, pp.7-8 provides field order and widths; CONTRACT.md p.16 requires 350 characters but the actual CVTRA05Y copybook is absent. Sequential offsets and trailing filler are inferred, not independently verified.
3. **A03 Cross-reference layout**: Use card number 1-16, customer ID 17-25, account ID 26-36 and filler 37-50. _Basis:_ Project Data Model, p.7 lists these fields and lengths; CONTRACT.md p.16 requires 50 characters; CVACT03Y itself is absent. Join account by card number without consulting account or customer files.
4. **A04 Transaction type layout**: Use type code 1-2, description 3-52 and filler 53-60. _Basis:_ CONTRACT.md p.16 names CVTRA03Y and a 60-character record; no reference-field layout is included in the wiki. The two-character code and 50-character description are assumed.
5. **A05 Category layout**: Use type code 1-2, numeric category 3-6, description 7-56 and filler 57-60; lookup key is type plus category. _Basis:_ CONTRACT.md p.16 names CVTRA04Y and a 60-character record; p.19 prints type and category; their reference-record layout and lookup key are unstated. The composite key prevents collisions between categories belonging to different types.
6. **A06 Character encoding**: Inputs are already decoded ASCII-compatible text; accept only printable ASCII within a record, including signed overpunch characters. Do not decode EBCDIC or packed binary. _Basis:_ CONTRACT.md p.16 says fixed-width text, one record per line, without specifying an encoding or binary conversion. Character positions equal byte positions only for this assumed text representation.
7. **A07 Line endings**: Accept LF or CRLF, with or without one final newline; empty file means zero records. Reject interior blank lines, extra blank records and solitary carriage returns. _Basis:_ CONTRACT.md p.16 says one record per line; line-ending and blank-record conventions are silent. No blank line is silently discarded as a transaction.
8. **A08 Record widths**: Require exact input widths 350, 50, 60 and 60 respectively; do not trim input records. Ignore filler and fields not used by the report. _Basis:_ CONTRACT.md p.16 fixes input widths; only output trailing spaces are explicitly optional on pp.16-17. Malformed used fields and record lengths fail; unused descriptive fields are not interpreted.
9. **A09 Signed amounts**: Read the 11-character transaction amount as signed display digits with implied two decimal places. Plain digits are positive; final {ABCDEFGHI encode positive 0-9 and }JKLMNOPQR negative 0-9. No decimal point or separate sign character is accepted. _Basis:_ Project Data Model p.8 gives S9(9)V99; pp.5 and 16 mention numeric conversion and fixed-width copybooks without specifying the text dump sign encoding. Packed decimal requires prior decoding; the chosen display representation may differ from the oracle dump.
10. **A10 Date defaults**: Absent startDate and endDate default independently to 2022-07-01 and 2022-07-31. Explicit empty values are invalid; require real Gregorian YYYY-MM-DD dates and startDate <= endDate. _Basis:_ CONTRACT.md p.16 supplies these dates; Reports acceptance criteria p.4 requires dates and valid ranges. No locale-dependent date parsing is used.
11. **A11 Selection date**: Select a transaction when the first ten characters of its processing timestamp fall within the inclusive requested range. Require a valid processing date on every transaction, even if ultimately excluded; ignore the timestamp time suffix for selection. _Basis:_ Project Data Model p.8 distinguishes origin and process timestamps; Reports pp.2 and 4 and CONTRACT.md p.16 do not identify which controls selection or how endpoints work. Origination date is not substituted when processing date is absent.
12. **A12 Batch filters**: Apply the date range only; do not add account, category or report-type filters to the batch request. _Basis:_ Reports and UI wiki pp.2 and 10-11 mention optional online filters; the isolated daily-report contract p.16 supplies only start and end dates. All accounts with selected transactions participate.
13. **A13 Detail semantics**: Emit one detail line per selected input transaction; do not consolidate duplicate transaction identifiers. _Basis:_ Reports p.2 calls the query aggregation, but CONTRACT.md p.19 specifies a transaction-ID detail line without grouping rules. Repeated identifiers remain distinct input occurrences.
14. **A14 Ordering**: Sort selected transactions by zero-padded 11-digit account, then transaction identifier, then original record position. Compare printable text case-sensitively. _Basis:_ CONTRACT.md p.16 requires printed order but neither the Reports wiki nor p.19 specifies sorting. Account details are contiguous and equal identifiers remain stable.
15. **A15 Identifier representation**: Require a 16-character nonblank transaction identifier, nonblank two-character type, four numeric category digits and 16 numeric card digits. Require numeric nine-digit customer and eleven-digit account identifiers in cross-references. Preserve transaction-ID spacing and case; print the account as its full eleven digits. _Basis:_ Project Data Model pp.7-8 gives lengths and numeric identifier types; CONTRACT.md p.19 allocates the printed widths but does not settle identifier formatting. Leading account and category zeros are retained.
16. **A16 Duplicate lookup keys**: Allow duplicate lookup records only when their meaningful fields agree. For cross-references meaningful fields include both customer and account; for descriptions compare text after removing trailing spaces. Reject conflicting duplicates even when unused. _Basis:_ The wiki identifies keys on p.7 but defines no duplicate-record policy for batch reference files. No arbitrary first or last match silently determines the report.
17. **A17 Missing lookup**: Require card-to-account, type description and composite category description for every selected transaction. Do not require lookups for excluded transactions. Empty descriptions in an otherwise present reference record are allowed. _Basis:_ Reports p.2 and the p.19 detail layout require account and reference descriptions, but lookup-failure handling is absent. An unresolved selected transaction fails the whole report rather than disappearing or receiving invented labels.
18. **A18 Pagination**: Use 50 detail rows per page. Headings, separators and total lines do not consume this detail-row allowance. Do not force a page break at an account boundary and do not create a trailing empty page. _Basis:_ CONTRACT.md p.19 specifies page headings and page totals but gives no page capacity or account-boundary rule. This is an explicit capacity assumption, not a recovered legacy page length.
19. **A19 Account totals**: Sum only selected transaction amounts for each account, carrying the running account total across page breaks. Print the account total and its following rule immediately after the account final detail, before a coincident page total. _Basis:_ CONTRACT.md p.19 defines account-total format and its following rule, not accumulation scope or coincident-boundary ordering. Each account has exactly one subtotal.
20. **A20 Page totals**: Sum only detail amounts on that page, excluding account subtotal lines; emit a page total and following rule after every nonempty page, including the final page. _Basis:_ CONTRACT.md p.19 defines page totals and following rules but does not explicitly define accumulation or final-page behaviour. No subtotal is added twice.
21. **A21 Grand total**: Sum all selected details once and print one grand-total line after the final page-total rule, with no additional rule. _Basis:_ CONTRACT.md p.19 supplies a grand-total layout and requires rules after page/account totals only. Grand total equals the sum of page totals and separately the sum of account totals.
22. **A22 Empty results**: Print one complete heading block followed by zero page total, its rule and zero grand total; omit account totals and details. _Basis:_ Reports acceptance criteria p.4 requires a zero-row report without error; p.19 does not specify its precise printed lines. Valid empty files and a valid range selecting no transactions succeed.
23. **A23 Exact arithmetic**: Keep amounts and all accumulations as integer cents; reject sums outside the JavaScript safe-integer range before precision is lost. No rounding is performed. _Basis:_ Project Data Model p.8 supplies two decimal places; CONTRACT.md pp.16-19 fixes decimal pictures without specifying arithmetic implementation. Fractional-cent drift cannot affect totals.
24. **A24 Printed amount pictures**: For detail -ZZZ,ZZZ,ZZZ.ZZ use minus for negative and blank for nonnegative. For +ZZZ,ZZZ,ZZZ.ZZ totals use explicit plus or minus. Suppress leading integer zeros and their commas, including the integer zero for zero values; retain decimal point and exactly two fractional digits. Normalize signed zero to nonnegative. _Basis:_ CONTRACT.md pp.17 and 19 defines pictures and leading-zero/comma suppression; signed-zero treatment is unspecified. Zero prints as a sign, spaces and .00 in the fifteen-character amount field.
25. **A25 Numeric overflow**: Reject a detail, page total, account total or grand total whose magnitude exceeds 999999999.99; also reject unsafe-integer accumulation. _Basis:_ CONTRACT.md p.19 allocates nine integer digits; overflow handling is not documented. No digits are truncated and no asterisk replacement is invented.
26. **A26 Text truncation**: Trim trailing reference-description spaces; take the first 15 type-description characters and first 29 category-description characters; left-align and space-pad. Preserve source width ten and transaction identifier width sixteen. _Basis:_ CONTRACT.md p.19 fixes X(15), X(29), X(10) and transaction-ID widths; handling longer reference text is unstated. Descriptions are truncated only to the explicit printed field widths.
27. **A27 Printed structure**: Use exactly the p.19 heading, blank, column heading and 133-hyphen rule; repeat them on each page. Fill all unallocated positions with spaces, emit no form feed, and return lines without embedded newline characters. _Basis:_ CONTRACT.md pp.16-19 specifies lines in printed order and allows returned strings or lists; no carriage-control convention is provided. Each returned report line is exactly 133 characters, although the contract permits omitting trailing spaces.
28. **A28 Failure contract**: Return status FAILED, a location-based error and no report lines for any detected input or financial-format failure; retain assumptions.md. Do not echo raw records or card values in errors. _Basis:_ Reports acceptance criteria p.4 requires surfaced errors; no batch failure format or partial-output policy is supplied. Failures are distinguishable from valid zero-row reports; no partial financial report is published.
29. **A29 Assumptions narrative**: A tool-less AI drafts English prose only from this decision ledger, never transaction records. Append the full ledger after any draft; if drafting fails, is malformed or is empty, return the ledger alone. _Basis:_ The maker requests every uncertain decision in assumptions.md; the wiki does not prescribe how to author that document or how authoring failure behaves. The report and authoritative decisions remain deterministic; narrative wording can vary and cannot remove the ledger.
30. **A30 Step isolation**: Read only the four daily-report files; do not post transactions, calculate interest, create statements, render PDFs or query external systems. Do not persist input records. _Basis:_ CONTRACT.md pp.16-17 lists the daily-report inputs and outputs separately; the online PDF flow is documented on pp.2 and 10-12. Upstream combined transactions are taken as supplied; no other step outputs are written.
