# Assumption register (extracted verbatim from the Transform script's assumption(...) calls)

1. **id**: A01 | **whatAssumed**: This core accepts decoded records and returns named JSON collections and assumptions text; it does not read or write physical files. | **wikiBasis**: posttran-opus.pdf p.12: CONTRACT.md requests fixed-width inputs and separate output files. Maker selected the decoded-record core with file decoding and delivery excluded.
2. **id**: A02 | **whatAssumed**: Use CONTRACT.md transaction/account/category field names; cross-references use card_num/acct_id and cards use card_num/card_acct_id/active_status. Ignore unused card/customer fields. | **wikiBasis**: posttran-opus.pdf pp.7,12: the contract defines output names but not decoded input naming. CardXref links card to account; Card.cardAccountId identifies its account.
3. **id**: A03 | **whatAssumed**: Process every input row once in supplied order, including repeated transaction IDs, using cumulative updated balances. No persistent replay protection exists. | **wikiBasis**: posttran-opus.pdf p.4: each transaction processed once; no duplicate-input, ordering or cross-run idempotency rule is provided.
4. **id**: A04 | **whatAssumed**: Resolve an account using the card cross-reference; missing cross-references and missing accounts reject the transaction. | **wikiBasis**: posttran-opus.pdf pp.2,7: fetch owning account; CardXref links card and account. Missing-link handling is absent.
5. **id**: A05 | **whatAssumed**: Only account and card active_status Y is active; every other one-character status is inactive. | **wikiBasis**: posttran-opus.pdf pp.3,4,7: account and card must be active; account status N is rejected. Active code definitions are not supplied.
6. **id**: A06 | **whatAssumed**: A card must exist and its card_acct_id must match the cross-reference account; otherwise reject. | **wikiBasis**: posttran-opus.pdf pp.3,7: card must be active and both ownership relationships are documented; missing-card and inconsistent-owner handling are absent.
7. **id**: A07 | **whatAssumed**: Use first-failure provisional rejects: 1 Card cross-reference not found; 2 Account not found; 3 Account inactive; 4 Card not found; 5 Card inactive; 6 Card account mismatch; 7 Credit limit exceeded. These are NOT authoritative legacy codes. | **wikiBasis**: posttran-opus.pdf p.3: TODO says to consult CBTRN01-03C for exact reject reasons; those sources are not supplied. Codes, descriptions and precedence are unspecified.
8. **id**: A08 | **whatAssumed**: Reject whenever the signed amount exceeds credit_limit minus current cumulative balance, including negative amounts when that formula fails. Rejects change no balance. | **wikiBasis**: posttran-opus.pdf pp.3,4: transaction must not exceed available credit; over-limit transactions are not posted. No separate credit/refund exception is stated.
9. **id**: A09 | **whatAssumed**: Add each posted signed amount to account current balance and to the category balance identified by account, type and category. Create a missing category from zero. | **wikiBasis**: posttran-opus.pdf pp.2,3,8: update account balances and add amount to matching category composite key; missing-category creation is unspecified.
10. **id**: A10 | **whatAssumed**: Positive amounts increase curr_cyc_debit; negative amounts increase curr_cyc_credit by absolute value; zero changes neither. Do not derive direction from type codes. | **wikiBasis**: posttran-opus.pdf pp.5,6: cycle credit and debit fields are listed, but posting sign rules and transaction-type direction mappings are absent.
11. **id**: A11 | **whatAssumed**: Preserve other account values and transaction timestamps. Do not add expiration, cash-limit, customer, disclosure-group, or reference-code validation. | **wikiBasis**: posttran-opus.pdf pp.2-4: posting rules specify active account/card, available credit and category increments only. The extra checks are not stated.
12. **id**: A12 | **whatAssumed**: Business date defaults to 2022-07-18 and is context only: no record date filtering or timestamp replacement. INTCALC parameter is unused. | **wikiBasis**: posttran-opus.pdf pp.4,10,12: business date selects a daily file and the contract gives this date; after file selection no row-date filter or timestamp stamping rule is specified. INTCALC is a different step.
13. **id**: A13 | **whatAssumed**: Use integer cents internally and fixed two-decimal output strings. Reject excess precision instead of rounding; signed account values allow ten integer digits, transaction/category values nine. | **wikiBasis**: posttran-opus.pdf pp.5,7,8,12: signed copybook numeric sizes and output maximum of two decimals are supplied; rounding and overflow recovery are not.
14. **id**: A14 | **whatAssumed**: All five input arrays and required scalar fields must exist. Malformed values, duplicate master keys or arithmetic overflow fail the entire calculation, with outputs null and a non-sensitive error; never expose a partial result. | **wikiBasis**: posttran-opus.pdf pp.5-8: types, required flags and unique/composite keys are supplied. Malformed-input, duplicate-master and overflow recovery rules are absent.
15. **id**: A15 | **whatAssumed**: Trim trailing ASCII spaces from text; enforce documented maximum widths and integer ID/code widths. Treat dates/timestamps as opaque text within their copybook widths rather than inventing calendar rules. | **wikiBasis**: posttran-opus.pdf pp.5-8,12: character widths and dates/timestamps are listed, and trailing spaces may be omitted; calendar-validation and invalid-date recovery are unspecified.
16. **id**: A16 | **whatAssumed**: Missing optional transaction text becomes an empty string and missing optional merchant_id becomes zero. Missing optional account reissue_date, addr_zip and group_id become empty strings. Required values are never invented. | **wikiBasis**: posttran-opus.pdf pp.6-8,12: these attributes are optional but the output field list is fixed; null/default conventions are not specified.
17. **id**: A17 | **whatAssumed**: Return all accounts and category balances, even untouched ones, with contract fields only; posted/rejected transactions preserve their normalized input field values. | **wikiBasis**: posttran-opus.pdf p.12: every account and every category balance after posting; transaction fields fixed; output order unrestricted.
18. **id**: A18 | **whatAssumed**: Empty daily input with valid master arrays succeeds unchanged. Every run starts from the supplied master snapshots, with no database writes, GDG advancement or scheduling. | **wikiBasis**: posttran-opus.pdf pp.3,4,10: empty daily file completes without posting; GDG semantics and exact schedule are TODO. The selected scope is the calculation core only.
19. **id**: A19 | **whatAssumed**: Every returned assumption has separate whatAssumed/wikiBasis properties and a Markdown table row. A model receives only this register to draft explanations, never financial records or decisions. | **wikiBasis**: Maker requested each assumption and its wiki basis. posttran-opus.pdf is silent on documentation generation; the confirmed design isolates wording generation from accounting.
20. **id**: A20 | **whatAssumed**: Retain every authoritative assumption verbatim. Accept a model explanation only for a recognized ID with exactly matching assumption and basis; failed, malformed or incomplete drafts fall back to register-only documentation without changing financial status or results. | **wikiBasis**: posttran-opus.pdf does not specify assumptions-drafting failures. Confirmed implementation default: documentation generation cannot discard financial results or authoritative assumptions.
21. **id**: A21 | **whatAssumed**: Do not produce interest outputs or optional flags, and do not claim oracle parity. | **wikiBasis**: posttran-opus.pdf pp.3,12,13: INTCALC is isolated from POSTTRAN; exact rejects are unresolved; optional flags reference PROTOCOL.md, which is not supplied.
